10M DiskANN on HDD — 로드·지연 실측과 prefetch 실행 판정

2026-08-05 최종보고 · 브랜치 wikipedia_hdd · Milvus 2.5.27 · 외장 USB HDD (5400rpm)

10M 벡터DB를 HDD에 로드까지 완주했고 검색 지연을 실측했다. 그 값이 검색 1회 400초이고, 이것이 prefetched-toolcall을 현재 구성에서 실행 불가능하게 만든다 — 질문당 예산 600초에 검색이 한 번밖에 들어가지 않는다. 측정 스위트는 Qdrant에서 Milvus DiskANN으로 전환을 마쳤다.

PART 1로드 — 에러 메시지가 스스로를 잘못 설명했다

적재는 이미 끝나 있었다. 문제는 로드였고, 네 겹을 벗겨야 했다. 각 층마다 표면에 보이는 원인과 실제 원인이 달랐다.

load segment failed, OOM if load, maxSegmentSize = 128.81 MB, memUsage = 26192.19 MB, predictMemUsage = 26321.00 MB, totalMem = 28020.16 MB thresholdFactor = 0.900000
표면상 원인실제 원인조치
메모리 부족 (26 GB 사용 중) 90%가 진행 중 세그먼트 로드의 예약치. 실사용 2,550 MB. 0.31초 만에 176개 승인 후 하나도 완료 못 함 taskExecutionCap 256 → 4
601초 만에 OOM OOM이 아니라 타임아웃 취소. OOM 문자열은 FailedLoadCache가 재생한 직전 실패의 잔상 loadTimeoutSeconds 600 → 36000
context canceled — 저장소 오류처럼 보임 세그먼트 하나짜리 120초 데드라인. 이 디스크에서 세그먼트 1개 로드가 14분 26초 걸린 적 있음 segmentTaskTimeout 120s → 3600s
컨테이너 exit=1, OOMKilled=false 메모리가 아니라 etcd 세션 상실. HDD 포화로 fsync가 밀려 리스 갱신 실패 etcd 볼륨만 SSD로 (인덱스는 HDD 유지)

호스트 쪽 두 겹

Docker Desktop 사망 (스왑 소진) — 로드가 100%에 닿은 직후 첫 검색에서 엔진이 죽었다. 호스트 36 GB인데 VM에 28 GB를 예약해 두고, 검색 단계에서 BGE-M3(2.1 GB)가 호스트에 올라오자 스왑이 25.4/26.6 GB로 터졌다. 적재와 검색은 메모리 요구가 다르다 — VM 크기를 앞 단계 기준으로 정한 것이 원인이었다. VM 28 → 18 GB로 낮춘 뒤 3시간 반 무사고 완주.

재시작 1회 = 5시간 — Milvus는 로컬 스토리지를 자기 캐시로 보고 기동 때 비운다 (roles.go: "Clean local data cache"). 재시작 직후 93 GB → 6.2 GB. DiskANN 인덱스를 MinIO에서 다시 받는데 MinIO도 같은 HDD에 있어, 한 스핀들에서 93 GB를 읽고 93 GB를 쓴다. 세그먼트당 로드가 로컬에 파일이 있을 때 약 2분, 콜드면 7–9분.

🧭 효과 없는 것으로 확인된 안 페이지 캐시 드롭 — GetUsedMemoryCount()는 statm의 RSS − Shared라 file-backed 페이지가 구조적으로 빠진다(6.5 GB 비워도 익명 RSS 변화 0 kB). mem_limit — min(cgroup, physical)이라 천장을 낮추기만 한다. mmap 플래그로 DiskANN 제어 — DiskANN은 항상 로컬로 내려받고 PQ 코드를 램에 둔다.

PART 2실측 — 검색 400초, 캐시로 안 내려간다

로드 완주 후 서로 다른 질의 10개. 같은 질의를 반복하면 페이지 캐시를 재게 되므로 재사용은 오류를 내도록 강제돼 있다.

† 철회된 수치. 당시 벤치마크가 같은 질의를 10회 반복해 2회차부터 페이지 캐시를 쟀다. 1M 값은 DEVLOG 기록으로만 남아 있고 원본 로그가 없다. 10M과 같은 선상에서 비교하면 안 된다.

10회차(272초)가 2회차(297초)보다 빠르지 않다. 로컬 인덱스 93 GB가 VM을 압도해 캐시가 들어설 자리가 없다. 검색 내내 디스크는 78 tps · 약 25 KB/transfer, 랜덤 IOPS 상한에 붙어 있었다.

캐시 비율을 10배 올려도 같다

searchCacheBudgetGBRatio 0.01 → 0.10 (Milvus 기본값) [1/3] 399,920.9 ms ← 0.01일 때 콜드 386초와 사실상 동일 캐시 예산 0.10 × 41 GB(원본 벡터) ≈ 4.1 GB 로컬 인덱스 93 GB → 4.4%만 캐시
✅ 이것이 좋은 소식인 이유 DEVLOG 7절이 "1M 부분집합은 최종 구성이 아니다 — 워킹셋이 캐시에 들어가면 HDD 처치가 약해진다"고 적어 뒀다. 10M에서 처치가 실제로 살아 있음이 확인됐다. Qdrant HNSW로 48분에도 안 끝나던 검색이 5분에 끝나고, 그 5분은 캐시로 지워지지 않는 진짜 매체 비용이다.

PART 3판정 — 이 구성에서 prefetch는 못 돌린다

QUESTION_TIMEOUT_SECONDS = 600 질문당 예산 검색 1회 = 400 s MAX_SEARCHES = 8 FanOutQA는 멀티홉 → 예산에 드는 검색 1회 → 전 문항 첫 검색 직후 타임아웃

돌려도 측정이 아니라 실패 카운트만 나온다. 그리고 이것은 설정 문제가 아니라 PLAN.md 5.1절이 이미 예고한 구조다.

retrievaldecode (8B가 Thought 하나)숨김 상한회수율
400 s약 2–5 s2–5 s0.5 – 1.3%
1 s1 s1 s50%

5.1절이 "검색이 decode보다 압도적으로 느리면 회수율은 0에 수렴한다 — 이건 강한 처치가 아니라 고장"이라고 적어 둔 바로 그 구간이다. 47M/Qdrant의 "48분에도 미완료"에서 5분으로 내려온 건 진전이지만, 의미 있는 구간(retrieval ≈ decode, 초 단위)에는 아직 못 왔다.

컬렉션을 로드하지 않고 측정

search()가 첫 호출에 지연 로드하는데 vectordb는 콜드를 먼저 잰다. 인덱스 읽는 몇 시간이 "검색 지연 첫 샘플"로 계상될 뻔했다. 게다가 load_timeout이 1M용 1800초를 상속해 30분에 죽었을 것이다.

가드 오탐 — 테스트가 버그를 고정

ps가 파이프라인 자식을 따옴표 없이 별도 행으로 내놓는데, 내 테스트는 래퍼 행만 먹여서 통과했다. 로그를 보면서 측정하면 실험이 거부되는 상태였다. 실행 파일 자리에서만 매칭하도록 고쳤다.
