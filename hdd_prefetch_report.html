2026-08-05 · 브랜치 wikipedia_hdd · Milvus 2.5.27 DiskANN · 10,000,000 rows · 외장 USB HDD

10M 벡터DB를 HDD에 올려 검색 지연을 실측하고, Target 모델이 검색할 때마다 상태를 동기화해 다음 검색을 미리 실행하는 prefetch 로직을 구현했다. 검색 지연 측정은 완료됐고, 그 값이 prefetch의 상한을 2% 미만으로 만든다. 쌍대 실험은 인프라 한계로 아직 완주하지 못했다.

PART 1실험이 돌아가게 만들기

적재는 이미 끝나 있었다. 문제는 로드가 안 됐다는 것이고, 에러 메시지가 스스로를 잘못 설명하고 있었다. 네 겹이었다.

load segment failed, OOM if load, maxSegmentSize = 128.81 MB, memUsage = 26192.19 MB, predictMemUsage = 26321.00 MB, totalMem = 28020.16 MB thresholdFactor = 0.900000

① memUsage의 90%는 메모리가 아니었다

Milvus는 이 값을 GetUsedMemoryCount() + committedResource.MemorySize로 계산한다. 자기 로그에 두 항을 따로 찍어 준다.

[committedMemSize(MB)=23641.75] [memUsage(MB)=26192.19] [mmapFieldCount=6] → 실제 프로세스 메모리 = 26192.19 − 23641.75 = 2,550 MB

23.6 GB는 진행 중인 세그먼트 로드가 잡아 둔 예약치다. 세그먼트당 약 128 MiB인데 이것도 DiskANN의 실제 메모리가 아니라 다운로드 버퍼 하한이다. 예약은 로드가 끝나야 반납되는데, 로그를 시계열로 보면 0.31초 만에 176개를 승인해 놓고 하나도 못 끝냈다. 승인 게이트 queryCoord.taskExecutionCap의 기본값이 256이다.

② "601초"는 OOM이 아니라 취소였다

queryCoord.loadTimeoutSeconds 기본값이 600이고, 로그에 ["load collection timeout, cancel it"] [loadTime=10m0.45s]가 찍혀 있다. 화면에 뜬 OOM 문자열은 FailedLoadCache가 들고 있던 직전 실패의 잔상을 ShowCollections가 되읽은 것이었다. 증상을 원인으로 읽고 있었다.

③ 그다음은 세그먼트 하나짜리 데드라인

①②를 고치자 세그먼트가 실제로 완료되기 시작했는데, 5분 뒤 로드가 통째로 풀렸다. At LoadBloomFilter: ... context canceled → release collection due to ref count to 0. segmentTaskTimeout 기본값이 120초인데 이 디스크에서 세그먼트 하나 로드가 14분 26초 걸린 적이 있다.

④ etcd가 스택을 죽이고 있었다

컨테이너가 exit=1, OOMKilled=false로 죽은 건 메모리가 아니라 etcd 세션 상실이었다. etcd는 쓰기마다 fsync하는데 로드가 HDD를 포화시키면 리스 갱신이 밀린다. DEVLOG 7절이 "규모를 키웠을 때 나타나면"이라고 적어 둔 리스크가 그대로 나타났다. etcd 볼륨(66 MB)만 내장 SSD로 옮겼다 — 인덱스는 HDD에 그대로다.

PART 2state-sync prefetch 로직

Target 모델이 검색할 때마다 그 시점의 상태를 drafter에 동기화하고, drafter가 예측한 다음 검색어를 미리 실행해 캐시에 넣는다. 다음 hop에서 실제 검색어가 예측과 같으면 대기가 0이 된다.

seam은 호출 하나

results = retriever.retrieve(query, state) ├─ 1. 캐시 조회 normalize(query) 로 키를 만들어 찾는다 ├─ 2. hit → 캐시 반환 아직 실행 중이면 재시작하지 않고 기다린다 │ miss → 실제 검색 └─ 3. sync + spawn state + (query, observation) 을 drafter 에 넘기고 예측된 다음 검색을 백그라운드로 실행

동기화를 "검색의 부수효과"로 만든 것이 설계의 핵심이다. 별도의 sync() 호출을 두면 agent 루프의 어느 분기에서 빠뜨릴 수 있고, 그러면 그 hop만 조용히 baseline으로 돌아간다 — 측정 기록에는 "prefetch 켜짐"이라고 남은 채로. 호출을 하나로 묶으면 그 실패 모드가 구조적으로 불가능하다.

왜 검색 완료 시점인가

다음 검색어를 예측하는 가장 강한 입력은 observation인데, 그건 검색이 끝나야 존재한다. 검색 시작 시점에 걸면 prefetch가 target 자신의 검색과 같은 디스크를 동시에 때린다. 이 HDD에서 희소 자원은 랜덤 IOPS(실측 78 tps)다.

완료 시점 = decode와 겹침

target이 다음 Thought를 생성하는 동안 디스크는 유휴다. 이 구간에 prefetch를 넣는 것이 PLAN.md 5.1절의 상한 hidden ≤ min(retrieval, decode)와 정확히 대응한다.

무결성 — 정확도가 움직일 수 없는 이유

캐시는 예측 문자열이 실제 질의와 정확히 같을 때만 쓴다. 불일치면 기존 경로를 그대로 탄다. 따라서 반환 passage가 baseline과 동일하고, prefetch는 언제 검색하느냐만 바꾼다.

🐛 이 보고를 쓰다가 잡은 버그 처음 구현은 정규화된 키만 보고 캐시를 내줬다. 그런데 prefetch는 자기가 예측한 문자열을 임베딩한다. BGE-M3는 대소문자·공백에 민감하므로 "Aurora Borealis"와 "aurora borealis"는 다른 벡터 → 다른 passage가 될 수 있는데, 키는 같아서 hit으로 처리됐다. 정확도 불변이 조용히 깨지는 구멍이고, 테스트가 그 동작을 고정해 두기까지 했다. 지금은 entry에 원문을 저장하고 원문 동일성을 요구한다. 정규화는 "같은 예측으로 중복 검색하지 않는다"는 원래 역할만 남았다.

⚠️ ReplayPredictor는 drafter가 아니다 현재 머신에 target/drafter 모델이 없다(AgentBench·llama.cpp·GGUF 모두 부재). 그래서 예측기는 에피소드의 검색어 순서를 그대로 재생하는 ReplayPredictor다. 이건 기구의 상한이지 적중률 측정이 아니다 — 구성상 항상 맞힌다. --wrong-hops로 일부러 빗나가게 해 miss·contention 경로도 밟게 하고, --think-seconds로 실제 모델이 쓸 추론 시간을 물린다. 서버가 생기면 HTTPPredictor(OpenAI 호환, llama-server·Ollama 양쪽)가 그대로 붙는다.

지금 구성에서 prefetch로 회수할 수 있는 비율은 2% 미만이다. 5.1절이 "검색이 decode보다 압도적으로 느리면 회수율은 0에 수렴한다 — 이건 강한 처치가 아니라 고장"이라고 적어 둔 바로 그 구간이다. 47M/Qdrant의 "48분에도 미완료"에서 5분으로 내려온 건 큰 진전이지만, 의미 있는 구간(retrieval ≈ decode, 초 단위)에는 아직 못 왔다.

🧪 그래서 쌍대 실험은 decode 간격을 측정된 중앙값에 맞춘다 임의의 값(예: 2초)을 넣으면 "1.7% 회수"라는 그 임의값에 대한 산수를 보고하게 된다. decode를 295초로 맞추는 것은 현실적인 에이전트를 흉내내는 게 아니라 decode가 retrieval만큼 길다면 기구가 실제로 숨기는가를 재는 것 — 기구의 상한 검증이지 운영 조건의 재현이 아니다.

PART 5막힌 지점 — Milvus가 아니라 Docker

지연 측정 직후 쌍대 실험을 돌리자 Docker 엔진이 죽었다. 메모리가 아니었다(호스트 여유 83%). Docker 자체 로그에 원인이 있다.

"error":"service fs failed: injecting event blocked for 60s"

fs는 /Volumes/agentic_rag/...를 VM 안으로 넣어 주는 파일공유(virtiofs) 서비스다. 이 서비스가 60초 블로킹되면 워치독이 죽이고 엔진이 같이 내려간다. 검색이 USB HDD를 IOPS 상한으로 계속 때리면 이 문턱을 넘는다.

사망시점원인
1회로드 완료 직후 첫 검색호스트 스왑 소진 (25,423 / 26,624 MB) — VM 28 GB + 인코더가 36 GB에 안 들어감
2회쌍대 실험 중service fs failed — 파일공유 워치독
3회재적재 25분 경과VM 응답 불능 → 고아 VM kill 후 복구
💸 재시작 1회 = 5시간 Milvus는 로컬 스토리지를 자기가 소유한 캐시로 보고 기동 때 비운다 (roles.go: "Clean local data cache"). 재시작 직후 93 GB → 6.2 GB. DiskANN 인덱스를 MinIO에서 다시 받아야 하는데 MinIO도 같은 HDD에 있다. 세그먼트당 로드가 로컬에 파일이 있을 때 약 2분, 콜드로 다시 받으면 7–9분. 컨테이너를 다시 만드는 모든 행위(compose 값 변경, Docker 재시작, VM 크기 변경)가 5시간짜리 재적재를 부른다.

이건 이 실험 플랫폼의 구조적 제약이지 설정 실수가 아니다. 인덱스가 bind mount 위에 있으므로 검색 경로 전체가 이 계층을 통과한다. 남은 선택지는 파일공유 구현 교체(gRPC FUSE), 동시 읽기 축소(beamWidthRatio), 또는 처치를 포기하고 인덱스를 SSD로 옮기는 것이다.

한 가지 되돌린 결정

searchCacheBudgetGBRatio를 0.01 → 0.10(Milvus 기본값)으로 되돌렸다. 캐시를 기본값의 1/10로 조인 건 "아무도 그렇게 안 쓴다"는 문제에 걸리는데, 이 프로젝트가 Qdrant 양자화 안을 기각한 논거가 정확히 그것(실제로 운용되는 구성이 아니다)이었다. 저장매체는 HDD 그대로이고 디스크 큐만 낮아진다.

다만 0.01에서 잰 수치(콜드 386 s / 중앙값 295 s)와 이후 수치는 서로 다른 구성이므로 직접 비교하면 안 된다. 3부의 값은 0.01 조건에서 측정된 것이다.
