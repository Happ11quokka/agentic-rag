# HNSW × HDD 부적합 진단

**작성일**: 2026-08-02
**브랜치**: `wikipedia_hdd`
**대상 컬렉션**: `wikipedia_2024_06_bge_m3_en_v1` (47,018,430 points, 209 GB, 외장 USB HDD)
**관련 문서**: [`DEVLOG.md`](DEVLOG.md), [`STATUS.md`](STATUS.md)

---

> ## 결론
>
> **버그가 아니라 하드웨어와 자료구조의 불일치다.**
>
> ```
> HNSW가 요구하는 것 : 랜덤 4 KB 접근 수만 회를 밀리초 안에
> HDD가 제공하는 것   : 랜덤 접근 초당 68회, 건당 16 KB 강제
> ```
>
> 검색 코드에는 결함이 없다. 무한루프도, 미종료도 아니다.
> HNSW는 **랜덤 접근이 싼 매체(램/SSD)를 전제로 설계된 자료구조**인데,
> 랜덤 접근이 가장 비싼 매체 위에 올려놨다.

## 1. 증상

| 조건 | 결과 |
|---|---|
| 기본 `ef` (=128), `limit=3` | **48분 17초 미완료** (19:25:56 → 20:14:13 수동 중단. 서버 타임아웃은 3600초로 확장해 둔 상태였음) |
| `hnsw_ef=16`, `limit=1` (8배 축소) | 240초 타임아웃에도 미완료 |
| 기본 `ef`, 종전 측정 | 900초 타임아웃에도 미완료 |

**콜드 쿼리는 끝내 완료되지 않았다.** 따라서 아래 수치는 전부 *하한*이다.

`ef`를 8배 줄여도 빨라지지 않은 것이 첫 단서였다. 그래프 탐색량이 병목이라면 대략 비례해 줄어야 한다.

## 2. 버그 가설 배제

"28분이나 걸리면 검색 코드가 잘못된 것 아닌가 — 무한루프이거나 빠져나오지 못하는 것 아닌가"라는 의심을 먼저 검증했다.

### 진단 증거

```
curl PID 24607                   ESTABLISHED       ← 연결 유지, 요청 진행 중
disk6 (외장 HDD)  iostat          64 / 59 / 81 tps  ← 지금도 활발히 읽는 중
                                 16.00 KB/t, ~1.09 MB/s
Qdrant 컨테이너 CPU               0.22 ~ 0.58%      ← CPU를 태우는 스핀 루프가 아님
optimizations.count               0                 ← 백그라운드 최적화 간섭 없음
GET /collections 응답             0.135초, HTTP 200 ← 서버 자체는 정상, 다른 요청 처리됨
```

### 판정

**CPU를 쓰지 않으면서 디스크만 계속 읽는 패턴**은 무한루프의 정반대다. 루프에 갇혔다면 이미 읽은 데이터를 반복 조회하므로 CPU가 튀고 디스크는 조용해야 한다.

또한 HNSW 탐색이 방문하는 노드 수를 역산하면 알고리즘상 설명 가능한 범위다.

```
68 tps × 2,897초(48분) ≈ 197,000회 읽기   ← 완료 전 중단이므로 하한
197,000 ÷ 96 세그먼트 ≈ 세그먼트당 2,050개 노드 방문 이상
```

`ef=128`로 49만 노드 그래프를 탐색할 때 방문 노드는 통상 `ef`의 5~10배다. 2,050은 그보다 높지만, Qdrant가 on-disk 세그먼트에서 실효 `ef`를 키우는 점을 감안하면 설명 가능하다. **알고리즘이 폭주하는 것이 아니라, 정상 동작이 이 매체에서 감당 불가능한 것이다.**

## 3. 실측 수치

### 저장매체

| 항목 | 값 | 측정 방법 |
|---|---|---|
| 디스크 | WD My Passport 2628, USB, APFS(Case-sensitive), 1.8 TB | — |
| 순차 쓰기 | 84 MB/s | `dd` 1 GB |
| **랜덤 읽기** | **68 IOPS** (64/59/81 tps 평균) | `iostat -d disk6` |
| **전송 단위** | **16.00 KB/t** | 동일 |
| 유효 대역폭 (랜덤) | ~1.09 MB/s | 동일 |

순차 84 MB/s ↔ 랜덤 1.09 MB/s — **같은 디스크에서 77배 차이**다.

### 검색 1회 (콜드)

```
19:25:56  CPU 2.10%  MEM 2.754 GiB / 27.36 GiB   ← 시작
19:39:59  CPU 0.58%  MEM 2.903 GiB / 27.36 GiB
19:53:59  CPU 0.32%  MEM 2.961 GiB / 27.36 GiB   ← 28분, 미완료
20:14:13                                          ← 48분 17초, 미완료 상태로 수동 중단

28분간 디스크에서 읽은 양   : 1.83 GB   (68 tps × 1,680s × 16 KB)
28분간 캐시에 남은 양       : 207 MiB   (2.754 → 2.961 GiB)
→ 읽은 것의 89%가 버려짐
```

램은 27.36 GB 중 **2.96 GB만 쓰였다.** 캐시에 여유가 넘치는데 채우지 못한다.

### 컬렉션 설정 (진단 시점)

```json
{ "vectors": { "size": 1024, "distance": "Dot", "on_disk": true, "datatype": "float32" },
  "hnsw_config": { "m": 16, "ef_construct": 100, "on_disk": true, "full_scan_threshold": 10000 },
  "optimizer_config": { "default_segment_number": 0, "max_segment_size": null,
                        "memmap_threshold": null, "indexing_threshold": 10000 },
  "quantization_config": null,
  "on_disk_payload": true }
```

`default_segment_number: 0`(auto)의 결과가 **세그먼트 96개**다. `qdrant.py::ensure_collection`은 `optimizers_config`를 넘기지 않으므로 이 값은 지정된 적이 없다.

## 4. 왜 안 맞는가 — 세 가지 메커니즘

### 4.1 HNSW의 접근 패턴은 본질적으로 랜덤이다

HNSW는 그래프를 따라 이웃 노드로 점프한다. 이웃 노드의 벡터는 183 GB 파일 안 **임의의 위치**에 있다. 인접성이 없다.

```
순차 읽기라면 : 114,000 × 16 KB = 1.83 GB ÷ 84 MB/s ≈ 22초
랜덤이라 실제 : 28분
→ 같은 데이터량, 77배 차이
```

OS readahead도 무력하다. 다음에 읽을 위치가 **그래프 탐색 결과에 의존**하므로 커널이 예측할 수 없다.

### 4.2 단일 쿼리 안에 재사용이 없다 → 캐시가 무력하다

HNSW 탐색은 한 쿼리 안에서 같은 노드를 두 번 방문하지 않는다. 재사용이 0이므로 캐시에 남길 이유가 없고, 커널은 16 KB를 읽어 4 KB만 쓰고 나머지를 회수한다.

**이것이 램 증설(Docker VM 8.2 → 27.4 GB)이 실패한 진짜 이유다.** 램이 부족했던 게 아니라 **캐싱할 가치가 있는 데이터가 없었다.**

> 캐시는 *이미 읽은* 데이터를 재사용하게 해줄 뿐,
> *처음 읽어야 할* 데이터의 seek 횟수를 줄이지 못한다.

### 4.3 4배 읽기 증폭

```
필요한 것 : 4 KB  (1024차원 × float32)
읽는 것   : 16 KB (KB/t 실측)
→ 필요량의 4배
```

HDD에서는 seek 시간이 지배적이라 전송량 자체는 큰 비용이 아니지만, 캐시 오염을 가중시켜 4.2를 악화시킨다.

### 4.4 세그먼트 96개가 곱해진다

Qdrant는 **세그먼트마다 독립적으로 탐색한 뒤 결과를 합친다.** `ef`는 세그먼트별로 적용된다.

```
총 탐색량 ≈ 세그먼트 수 × ef = 96 × 128
```

`ef`를 128→16으로 8배 줄여도 안 빨라졌던 이유가 이것이다. 세그먼트 96개를 도는 **고정 오버헤드**가 지배적이라 `ef` 축소분이 묻혔다.

## 5. 대응 선택지

### (A) 응급처치 — 지금 구성을 살린다

| 변경 | 효과 | 결과 변화 |
|---|---|---|
| 세그먼트 96 → 4 | 탐색 횟수 24배 감소 | **recall 하락** (총 탐색량 96×128 → 4×128) |
| `hnsw_config.on_disk: false` | 그래프 2.8 GB 램 상주 → 링크 읽기 제거 | **없음** (같은 그래프, 위치만 이동) |

```
예상: 114,000회 → ~1,600회  →  약 50초
```

목표(2~10초, decode 1 hop과 동급)에는 **여전히 5~25배 못 미친다.** 남은 격차는 여러 쿼리를 돌린 정상상태(warm)에서 메워야 하며, 이는 병합 후 실측으로 확인해야 한다.

- 재색인 필요. HDD 위 209 GB 재작성으로 수 시간 예상
- **SSD 대조군에 동일 설정을 적용**해야 비교 성립
- 세그먼트 수는 `QdrantConfig`에 설정 항목이 없어 코드 추가 필요. 기존 컬렉션은 REST PATCH로 변경 가능(재적재 불필요)

### (B) 권장 — Qdrant에서 DiskANN의 핵심 기법을 그대로 쓴다

**백엔드를 바꾸지 않고도** 아래 설정으로 DiskANN과 같은 구조를 만들 수 있다.

```jsonc
// 컬렉션
"quantization_config": { "binary": { "always_ram": true } },
"hnsw_config":         { "on_disk": false },
"optimizers_config":   { "default_segment_number": 4 }

// 검색
"params": { "quantization": { "rescore": true, "oversampling": 2.0 } }
```

동작 원리가 DiskANN과 동일하다.

| | DiskANN | Qdrant 위 설정 |
|---|---|---|
| 탐색 중 거리계산 | 램의 PQ 압축본 | **램의 binary 압축본** |
| 최종 순위 | 후보만 원본 벡터로 재계산 | **`rescore: true`가 원본 float32로 재계산** |
| 그래프 | Vamana (홉 수 적음) | HNSW (`on_disk: false` → 램 상주) |

용량이 맞는다.

```
binary 압축 : 1024차원 × 1비트 = 128 B/벡터
47M × 128 B = 6.0 GB
+ HNSW 그래프  2.8 GB
= 8.8 GB       ← 램 27.4 GB에 여유롭게 들어감
```

**그래프도 압축벡터도 램에 있으면 탐색 중 디스크 접근이 0회다.** 디스크는 마지막 rescore 때만 건드린다.

```
탐색    : 디스크 0회
rescore : 후보 ~300개 × 4 KB = 300회 ÷ 68 IOPS ≈ 4~5초
```

#### 처치가 오히려 깔끔해진다

현재는 HDD↔SSD 차이에 그래프 탐색·링크 읽기·벡터 읽기가 뒤섞여 있다. 이 설정에서는 디스크가 관여하는 지점이 **"원본 벡터 읽기" 하나로 좁혀진다.** 저장매체 차이가 정확히 그 항목만 반영하므로 인과 설명이 단순해진다.

#### 비용과 위험

- **재색인 1회.** (A)와 같은 작업이므로 추가 비용이 없다. 재적재·재다운로드 불필요
- **binary 양자화가 BGE-M3에서 얼마나 정확한지 미검증.** Qdrant 문서가 검증했다고 밝힌 목록은 주로 OpenAI·Cohere 계열이다. 1024차원이라 가망은 있으나 `rescore`로 얼마나 회복되는지는 재봐야 한다
- → **47M 재색인 전에 소규모 컬렉션(수십만 건)을 SSD에 만들어 양자화 유무의 recall을 비교한다.** 한 시간 내 판정 가능하며, 수 시간짜리 재색인을 헛되이 쓰는 위험을 없앤다

### (C) 보류 — 백엔드를 Milvus DiskANN으로 교체

DiskANN(Subramanya et al., NeurIPS 2019)은 **벡터를 디스크에 두는 것을 전제로** 설계된 ANN이다. 디스크 읽기를 줄이는 장치가 셋 있다.

| | HNSW (현재) | DiskANN |
|---|---|---|
| 그래프 | 계층형, 근거리 이웃 위주 | **Vamana** — α-가지치기로 장거리 간선 확보 → 홉 수 감소 |
| 벡터 저장 | 그래프와 **분리** → 노드마다 별도 읽기 | **벡터 + 이웃목록을 같은 섹터에 배치** → 읽기 1회 |
| 탐색 중 거리계산 | 원본 벡터 필요 → 매번 디스크 | **램의 PQ 압축본으로 근사** → 탐색 중 디스크 접근 없음 |
| 최종 순위 | — | 후보만 원본 벡터로 재계산 |

세 번째가 핵심이다. 47M × 128 B ≈ **6 GB**면 압축본 전체가 램(27 GB)에 들어간다.

```
예상: 질의당 수백 회 읽기 → 300회 ÷ 68 IOPS ≈ 4~5초
```

(B)와 같은 구간이다. 다만 **(B)는 같은 결과를 백엔드 교체 없이 얻는다.** DiskANN 고유의 이점은 Vamana 그래프(홉 수 감소)와 벡터·이웃목록 동일 섹터 배치인데, (B)에서 탐색이 이미 램에서 끝나므로 그 이점이 발휘될 여지가 크지 않다.

#### 실험 타당성 측면에서 더 중요한 논점

> "HNSW를 HDD에 올리는 구성을 실제로 쓰는 곳이 있는가? 처치가 허수아비 아닌가?"

정당한 지적이다. HNSW는 램 상주를 전제로 설계됐고, **디스크에 벡터를 두는 실제 시스템은 DiskANN 계열을 쓴다.** 현 구성은 "느린 저장매체"가 아니라 "잘못 고른 자료구조"를 측정하고 있다고 볼 여지가 있다.

DiskANN으로 가면 다음 문장이 성립한다.

> *"디스크 기반 ANN의 정석 구성에서 저장매체를 SSD → HDD로 바꾸면
> 검색 지연이 얼마나 늘고, 그것이 decode 뒤에 얼마나 숨겨지는가"*

#### 비용

- **Qdrant는 DiskANN을 지원하지 않는다** (HNSW만). 백엔드 교체가 필요하다
- 이 브랜치에 `wikipedia/src/wikipedia/milvus.py`가 있고 `index_type`이 설정 가능하다 (현재 기본 `AUTOINDEX`). **Milvus는 `DISKANN`을 지원**하므로 경로는 열려 있다
- **재적재 필요.** 원본 parquet은 삭제됨(STATUS.md: "원본 parquet 잔여 0개") → 재다운로드 시 회선 6 MB/s로 13시간
  - 대안: Qdrant에서 scroll로 벡터 추출. ID 순이라 대체로 순차 접근이므로 183 GB ÷ 84 MB/s ≈ 1시간 내외로 끝날 가능성 (검증 필요)
- Milvus 공식 문서는 DISKANN에 **NVMe SSD를 요구**한다. HDD는 지원 범위 밖이라 문서 수치대로 안 나올 수 있다

### 채택하지 않은 안

| 안 | 사유 |
|---|---|
| **rescore 없는** 양자화 | 최종 순위까지 압축본으로 매기면 검색 결과가 실제로 바뀐다. `rescore: true`가 반드시 붙어야 한다 |
| `ef` 낮추기 | recall이 바뀌어 대조군과 비교 불가. 게다가 §4.4에서 보듯 효과도 없었다 |
| 코퍼스 축소 | 워킹셋이 캐시에 들어가 HDD 처치가 무의미해짐 |
| float16 전환 | 벡터 크기가 절반이 되어 처치 강도가 바뀜. 재적재 13시간 |

> **정정**: 이 문서 초안은 양자화 전체를 "검색 정확도가 변해 실험 타당성 훼손"으로 배제했다.
> 그러나 그 논리를 적용하면 DiskANN의 PQ도 똑같이 배제해야 한다. 실제로 문제가 되는 것은
> *최종 순위를 압축본으로 매기는 것*이며, `rescore: true`를 쓰면 순위는 원본 float32로 계산된다.
> 후보 선별이 근사인 것은 HNSW가 이미 근사인 것과 같은 성격이다.

> §1~§4의 진단 내용은 그대로 유효하다.

1. **recall 사전 검증 (먼저, 1시간 내).** 소규모 컬렉션(수십만 건)을 SSD에 만들어 binary 양자화 + `rescore` 유무의 recall을 비교한다. 47M 재색인에 수 시간 쓰기 전에 판정한다
2. **통과하면 (B)를 한 번의 재색인으로 적용.** 세그먼트 4개 + `hnsw.on_disk: false` + binary 양자화(`always_ram`)를 동시에 건다. 셋 다 같은 재색인에 묶이므로 나눠 하면 수 시간씩 손해다
3. 미달 시 (A)만 적용된 상태로 콜드/웜 재측정 → 그래도 부족하면 **(C) 정식 검토**
4. 어느 쪽이든 **SSD 대조군에 동일 설정**을 적용해야 비교가 성립한다

### 남은 과제 (이 문서 범위 밖)

- **SSD 대조군 미구축.** 현재 treatment만 존재한다
- **AgentBench 미연동.** `AgentBench/`·`repro/` 전체에서 Qdrant 참조 코드가 0건이다. 에이전트는 아직 이 DB를 쓰지 않는다
- **세그먼트 수 설정 항목 부재.** `QdrantConfig`에 `default_segment_number`가 없다(`qdrant.py`). 기존 컬렉션은 REST PATCH로 바꿀 수 있으나, 재현성과 SSD 대조군 구축을 위해 필드 추가가 필요하다
